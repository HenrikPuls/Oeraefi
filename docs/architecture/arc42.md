## 1. Introduction and Goals

Historical economic sandbox game, Iceland Settlement Period (Landnám, c. 874–930 CE). Full design rationale: `docs/concept/`.

**Quality goals (draft — refine once implementation starts):**
- Maintainability: data-driven balancing (skills, prices, origins) editable without code changes
- Performance: NPC economy simulation must scale to many farms without frame-rate impact
- Extensibility: new skills/goods/buildings addable via data assets, not code changes

**Stakeholders:** Henrik (solo developer / designer)

## 2. Constraints

| Constraint | Decision | Rationale |
|---|---|---|

| Rendering | 3D terrain mesh + orthographic camera at isometric angle | Avoids tiling seams on irregular real coastline data; see concept doc 12 |

## 3. Context and Scope

Single-player, no online services, no external system integrations. To be detailed once the first external interfaces (if any — e.g., save file format, mod support) are defined.

## 4. Solution Strategy

- **Two-tier economy simulation:** detailed agent simulation for farms near the player, abstracted tick-based calculation for distant farms (concept doc 4.1)
- **Data-driven balancing:** ScriptableObjects for skills (11.6), origins (11.1), price tables (14.6), calendar (7) — balancing changes should not require code changes or recompilation
- **Emergent state over scripted events:** mortality/health driven by a continuous Vitality resource affected by supply, cold, and disease, not isolated random-roll death checks (concept doc 11.5)
- **Task assignment over direct control:** workers (thralls, free household members) are assigned roles and execute autonomously; the player manages priorities, not individual actions (concept doc 4.5/10)
- **Hidden internal state, qualitative UI:** morale/discontent values are computed exactly internally but never surfaced as exact numbers to the player (concept doc 4.5/10)

## 5. Building Block View

Assembly layout (since M0):

| Assembly | Location | Purpose |
|---|---|---|

| `Oerfi.Editor` | `Assets/Scripts/Editor/` | Editor tooling: SO/scene generators, batchmode entry points (`-executeMethod`) |

Implemented modules (M2): **Core** (`Season`, `ITickable`, `CalendarModel` — pure C# 364-day Old Icelandic calendar with Aukanœtr + Sumarauki leap week, ADR-free design decision in code docs) and **Economy** (`Good`, `PricingConfig`, `PricingEngine`, `FarmEconomyAgent`, `IEconomyDetailLevel` + detailed/abstracted strategies + `EconomyLevelSelector`). Balancing data assets live under `Assets/Data/` (generated by `Oerfi.Editor.Economy.GoodAssetGenerator`, which creates missing assets with concept-table values and only verifies/warns on existing ones — user balancing is never overwritten).

Implemented modules (M3): **Characters** (`AttributeId`/`Attributes` struct with named fields, `SkillId`, `Origin`/`OriginProfile` SO — one asset per origin under `Assets/Data/Characters/Origins/`, `SkillGrowthConfig` SO, `SkillSystem` learning-by-doing with diminishing returns, `CheckResolver` 2d10 roll-under with injectable `IRandomSource` (inclusive bounds), `Character` + `CharacterFactory`) and **Household** (`ConcealedScalar` base + `IConcealedStateDisplay` as the ONLY UI contract for hidden state, `MoralValue`, `VitalityValue` (death emergent at 0), `UnrestSystem` (concept risk bands 30/60/90 + thrall-coordination multiplier), `ClothingVitalityLink` (clothing deficit → vitality, never moral), `ThrallSupplyNeed` (static need functions, season as parameter), `HouseholdGoodsStock` (aggregate target/actual per category), `ManumissionService`). Character data assets are generated by `Oerfi.Editor.Characters.CharacterAssetGenerator` under the same create-with-values/verify-don't-overwrite policy.

Implemented modules (M4): **AI** (`TaskRole` — 18 labour roles with German game-content names in XML docs; `SeasonalWindow`/`TaskRoleDefinitions` — only Fowling, Trading and Farming are gated to summer months 0–5; `AutonomousWorker` — base yield × (1 + skill/10), learning-by-doing, overload→unrest coupling via named constants +0.5/tick overload, −0.1/tick passive recovery, Toughness threshold 7; one unified `Tick(monthIndex, outputGood, heavyWork)` feeding `FarmEconomyAgent` stock; `PriorityOverride` — role reassignment + active toggle without reflection) and **Terrain** (`TerrainMetadata` — JsonUtility DTO bound 1:1 to the pipeline's metadata schema; pure `HeightmapDecoder` implementing the ADR-005 encoding `raw = clip(height_m × 10 + 10000)` with metadata-driven scale/offset, sea/nodata → 0 m, vertical flip, 2ⁿ+1 resolution snap; `TerrainResourceLayer` SO — flat row-major arrays for forest density / spring type / erosion, user-tunable regeneration rate; plain-class `ForestRegenerationTick : ITickable`; `ForestHeuristic` — initial density from elevation (fade 200→450 m) and slope (≤ 30°), code constants with M13 SO-ification candidate). Region assets: `Assets/Terrain/<Region>TerrainData.asset` (derived data, re-import overwrites in place) and `Assets/Data/Terrain/<Region>TerrainResourceLayer.asset` (balancing-bearing, create-once); both git-LFS-tracked. The first real-heightmap import (southwest, 2049², 102.45 km extent) ran via batchmode.

Non-asset directories outside `Assets/`: `scripts/` (verification gate), `tools/terrain/` (scripted DEM pipeline: fetch → process, ADR-005), `terrain-cache/` (gitignored DEM source tiles + temp), `docs/archive/` (predecessor project history bundle).

Terrain data path: `Assets/StreamingAssets/Terrain/` holds the processed heightmap (canonical: UInt16 little-endian RAW; encoding `raw = clip(height_m × 10 + 10000)`, 0 = sea) plus metadata JSON — git-LFS tracked (`*.raw`, `*.png`). See ADR-005 and `docs/pipeline/terrain-import.md`.

Anticipated top-level runtime modules (see `CLAUDE.md` directory structure): Economy, Characters, Buildings, Weather, AI (task assignment).

## 6. Runtime View

First scenario (implemented as of M2, runtime wiring pending M5):

**Daily tick:** a runtime driver calls `CalendarModel.AdvanceDay()` → season boundary check fires `SeasonChanged`/`OnSeasonChange` first → then `DayChanged` + `OnDayTick(TotalDays)` to all registered `ITickable`s. `FarmEconomyAgent.Tick` is currently invoked explicitly by tests/future callers and delegates its mechanics (spoilage → priority consumption → production) to the injected `IEconomyDetailLevel` strategy (detailed vs. abstracted by distance via `EconomyLevelSelector`); the calendar↔agent wiring lands with the playable slice (M5).

Further scenarios to be added as implemented: task assignment resolution, trade ship arrival/departure, mortality resolution.

**M4 simulation pieces (wiring pending M5):** `AutonomousWorker.Tick` is invoked per simulated day with the calendar month index and feeds its yield into the farm's `FarmEconomyAgent` stock; seasonal role availability keys off the same month index. `ForestRegenerationTick` is an `ITickable` registered with the `CalendarModel` and advances forest regeneration once per day. The worker's role→good mapping and the heavy-work classification per role are caller-side until the M5/M6 data tables exist.

## 8. Cross-Cutting Concepts

- **Data-driven configuration:** all balancing values (skills, prices, calendar, origins) live in ScriptableObject assets, not hardcoded
- **Two-tier simulation detail:** near/far distinction for economy agents (performance concern)
- **Hidden-state UI principle:** discontent/morale never shown as an exact number or bar — only qualitative, behavior-based signals with intentionally fuzzy thresholds (concept doc 4.5/10). Code contract: UI may bind only to `Oerfi.Household.IConcealedStateDisplay.GetDisplayStage()`; raw values (`RawValue`) are simulation-internal
- **Asset generation via editor scripts:** scenes, prefabs, and SO assets are created by `Oerfi.Editor` code run through Unity batchmode (`-executeMethod`); `.unity`/`.prefab` YAML is never hand-edited. Two policies: balancing-bearing assets (goods, origins, resource layers — user-tunable values) are created once and verified/warned on drift, never overwritten; derived data (TerrainData — fully reproducible from RAW + metadata) is updated in place on re-import (GUID-stable)
- **Local verification gate:** `scripts/run-tests.ps1` runs Unity batchmode tests (EditMode always; PlayMode when runtime-relevant) and parses the results XML; this is the pre-commit gate until CI exists (CLAUDE.md)

## 11. Risks and Technical Debt

| Risk | Mitigation |
|---|---|
| "Chore simulator" feel (busywork instead of meaningful decisions) | Task-assignment automation, aggregate stock tracking instead of per-item micromanagement (concept doc 4.5/10) |
| Agent-based economy simulation performance at scale | Two-tier detail model (near/far) |
| Balancing drift between concept doc and implementation | arc42 + concept doc kept explicitly separate; price/skill tables sourced from concept doc sections 11.6/14.6 as single source of truth for initial values |
| Migrated legacy code (predecessor project) may not meet current conventions/tests | Module-by-module adoption in M2–M4 with ported tests required green in the new gate before each module counts as migrated |

Technical debt: none recorded yet beyond the migration risk above (M0 just established the baseline).
